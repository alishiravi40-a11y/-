# راهنمای اعتبارسنجی محلی و آزمون پچ امنیتی پایگاه‌داده (Supabase & PostgreSQL)

این راهنما برای راهبری و اجرای آزمون‌های پایگاه‌داده در یک **محیط کاملاً محلی، ایزوله و موقت** تدوین شده است تا پچ امنیتی سخت‌سازی توابع `SECURITY DEFINER` و سیاست‌های `RLS` (مربوط به پیش‌نویس مرحله ۱۵) بر روی یک دیتابیس تمیز و بدون ریسک تست شود.

---

## ۱. پیش‌نیازهای محیط آزمایش

پیش از شروع، مطمئن شوید که محیط اجرای آزمون دارای ویژگی‌های زیر است:
- **محیط سخت‌افزاری:** یک رایانه شخصی یا سرور توسعه اختصاصی متعلق به خودتان (ترجیحاً با حداقل ۸ گیگابایت حافظه رم).
- **محیط کانتینری:** نصب و فعال بودن موتور Docker (یا ابزار سازگار با داکر).
- **ابزار خط فرمان:** نصب بودن ابزار رسمی Supabase CLI.
- **شاخه کاری ایزوله:** ایجاد یک نسخه کپی یا شاخه جداگانه (Branch) از مخزن کد پروژه.
- **ممنوعیت داده‌های واقعی:** در این محیط نباید تحت هیچ شرایطی از داده‌های واقعی، نسخه‌های پشتیبان دیتابیس اصلی یا اطلاعات مشتریان استفاده شود.

---

## ۲. کنترل نسخه ابزار و مشاهده راهنما

پیش از اجرای هر فرمان، کاربر باید ساختار دستورات را با سوئیچ راهنما (`--help`) و نسخه نصب‌شده تطبیق دهد تا از حدس زدن گزینه‌ها جلوگیری شود:

```bash
supabase --version
supabase --help
supabase init --help
supabase start --help
supabase migration new --help
supabase db reset --help
supabase test db --help
supabase db advisors --help
```

> **نکته کلیدی:** تمام دستورات باید صرفاً مطابق با مستندات رسمی نسخه نصب‌شده شما اجرا شوند و نباید گزینه‌ای از روی حدس وارد شود.

---

## ۳. قوانین سخت‌گیرانه ایزوله‌سازی (فرمان‌های ممنوع)

برای جلوگیری از هرگونه نشت اطلاعات یا آسیب به پایگاه‌داده واقعی، رعایت اصول زیر الزامی و حیاتی است:

- **ممنوعیت پیوند:** پروژه محلی نباید به هیچ عنوان به پروژه اصلی Supabase پیوند داده شود.
- **فرمان‌های اکیداً ممنوع:**
  - `supabase link` ❌ (ممنوع)
  - `supabase db push` ❌ (ممنوع)
  - `supabase db reset --linked` ❌ (ممنوع و به شدت تخریبی برای دیتابیس راه دور)
- **پاکسازی متغیرها:** هیچ کلید محرمانه، نشانی دسترسی یا رمز عبور مربوط به پروژه آنلاین نباید در متغیرهای محیطی نشست آزمایش قرار گیرد (`unset SUPABASE_URL DATABASE_URL POSTGRES_URL SUPABASE_SERVICE_ROLE_KEY`).
- **پشته تمام‌محلی:** تمام اتصالات باید منحصراً به کانتینرهای محلی ۱۲۷.۰.۰.۱ متصل باشند.

---

## ۴. مراحل آماده‌سازی محیط محلی

عملیات را گام به گام به ترتیب زیر انجام دهید:

1. **تهیه پشتیبان:** از وضعیت فعلی کدهای پروژه خود یک نسخه پشتیبان مطمئن تهیه کنید.
2. **شاخه کاری جدید:** یک شاخه جدید گیت (مثلاً `git checkout -b test/db-hardening`) بسازید.
3. **بررسی عدم اتصال دوردست:** اطمینان حاصل کنید پوشه `.supabase/remote` یا تنظیمات اتصال به سرور آنلاین وجود ندارد.
4. **راه‌اندازی ساختار محلی:** دستور `supabase init` را اجرا کنید.
5. **شروع سرویس‌های محلی:** دستور `supabase start` را اجرا نمایید.
6. **ثبت وضعیت بدون نشت رازها:** از شروع موفق تمام کانتینرهای محلی مطمئن شوید؛ از انتشار کلیدهای چاپ‌شده در ترمینال خودداری فرمایید.
7. **بازنشانی محلی پایگاه‌داده:** دستور `supabase db reset` را در محیط محلی اجرا کنید.
8. **اثبات مهاجرت‌های پایه:** مطمئن شوید تمام ۲۳ فایل مایگریشن موجود در پوشه `supabase/migrations` بدون هیچ خطایی روی دیتابیس محلی اجرا شده‌اند.

---

## ۵. تولید مایگریشن رسمی آینده

برای تبدیل پیش‌نویس پچ مرحله ۱۵ به یک مایگریشن استاندارد:

1. **ایجاد فایل جدید:** با استفاده از دستور رسمی زیر، فایل مهاجرت جدید را بسازید:
   ```bash
   supabase migration new rls_security_definer_hardening
   ```
2. **عدم نام‌گذاری دستی:** از نام‌گذاری دستی فایل‌ها بپرهیزید تا توالی زمانی و ترتیب Supabase رعایت شود.
3. **انتقال محتوای اجرایی:** محتوای فایل پیش‌نویس `security/sql-drafts/rls_security_definer_hardening_draft.sql` را با دقت به فایل مایگریشن تولیدشده انتقال دهید.
4. **حذف محافظ‌های پیش‌نویس:** در فایل مایگریشن تولیدشده، این بخش‌های محافظتی که مختص پیش‌نویس بوده‌اند را حذف کنید:
   - هدرهای هشدار `DRAFT ONLY`
   - بلوک متوقف‌کننده `RAISE EXCEPTION`
   - دستور `BEGIN` در ابتدای فایل
   - دستور `ROLLBACK` در انتهای فایل
5. **عدم دستکاری فایل پیش‌نویس اصلی:** فایل پیش‌نویس `security/sql-drafts/rls_security_definer_hardening_draft.sql` باید دست‌نخورده باقی بماند.
6. **بررسی توسط متخصص:** انتقال باید توسط متخصص دیتابیس بازبینی و کنترل نهایی شود.

---

## ۶. گردش کار آزمون پایگاه‌داده (pgTAP)

پس از افزودن مایگریشن جدید:

1. **بازنشانی کامل دیتابیس محلی:**
   ```bash
   supabase db reset
   ```
2. **اجرای آزمون‌های pgTAP:** با اجرای دستور زیر، آزمون‌های اعتبارسنجی موجود در `supabase/tests/rls_security_definer_hardening_test.sql` را اجرا کنید:
   ```bash
   supabase test db
   ```
3. **بررسی مشاور امنیتی دیتابیس:** در صورت پشتیبانی نسخه CLI شما:
   ```bash
   supabase db advisors
   ```
4. **بررسی دقیق خروجی‌ها:** گزارش‌ها و لاگ‌ها را بررسی کنید تا هیچ اخطار یا خطایی وجود نداشته باشد.
5. **تکرار آزمون:** آزمون را روی یک دیتابیس تازه ریست‌شده مجدداً تکرار کنید تا از تکرارپذیری آن اطمینان حاصل شود.

---

## ۷. معیارهای قبولی و موفقیت (Success Criteria)

مرحله آزمایش زمانی موفق قلمداد می‌شود که همه شرایط زیر برآورده شده باشند:
- [x] تمام مهاجرت‌ها (از ۰۱ تا مایگریشن جدید سخت‌سازی) بدون کوچکترین خطا اعمال شوند.
- [x] تمام ۹۳ آزمون assertion موجود در بسته `pgTAP` با موفقیت پاس (PASS) شوند.
- [x] نقش‌های `anon` و `authenticated` هیچ‌گونه دسترسی مستقیم (SELECT, INSERT, UPDATE, DELETE) روی جداول `cheques` و `order_invoice_conversions` نداشته باشند.
- [x] هفت تابع حساس پایگاه‌داده فقط و فقط توسط نقش `service_role` قابل فراخوانی باشند.
- [x] تمام هفت تابع دارای `SET search_path = ''` باشند و هیچ ارجاعی به `pg_temp` نداشته باشند.
- [x] هیچ داده واقعی یا محیطی خارج از ساندباکس محلی تحت تأثیر قرار نگرفته باشد.
- [x] آزمون‌های نرم‌افزاری برنامه (`npm test`) همچنان با موفقیت پاس شوند.

---

## ۸. مدارک لازم برای بازگشت و گزارش در گفتگو

پس از اتمام موفقیت‌آمیز آزمون محلی، فقط مستندات زیر را جهت ادامه فرآیند در گفتگو ارسال فرمایید:
- شماره نسخه Supabase CLI
- خروجی متنی دستور `supabase db reset`
- خروجی متنی دستور `supabase test db`
- خروجی بررسی مشاور امنیتی (`supabase db advisors`)
- نام دقیق فایل مایگریشن تولیدشده
- هش SHA-256 فایل مایگریشن تولیدشده
- لیست هرگونه هشدار یا پیام سامانه
- **هشدار اکید:** از ارسال هرگونه کلید دسترسی، توکن، رمز عبور یا شناسه پروژه جداً خودداری کنید.

---

## ۹. خط‌مشی ممنوعیت انتشار مستقیم به محیط عملیاتی

- **عدم کفایت آزمون محلی:** موفقیت در محیط محلی به تنهایی به معنای مجوز انتشار مستقیم بر روی محیط پروداکشن (Production) نیست.
- **لزوم محیط مرحله‌بندی (Staging):** پس از موفقیت محلی، مایگریشن باید ابتدا بر روی یک پایگاه‌داده مجزای Staging تست شود.
- **شرط استقرار پروداکشن:** اعمال نهایی بر روی پایگاه‌داده عملیاتی صرفاً پس از تهیه نسخه پشتیبان کامل (Full Backup)، تدوین سناریوی دقیق بازگشت (Rollback Plan) و اخذ تاییدیه نهایی مدیر ارشد سامانه مجاز خواهد بود.
