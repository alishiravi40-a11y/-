# beta — ماژول فروش اقساطی بتا (هسته v0.4)

طراحی: `docs/BETA_INSTALLMENTS_DESIGN_FA.md` (v0.6).
- قواعد در **پایگاه داده** اعمال می‌شوند: `core/schema/004_beta.sql`.
- این بسته فقط داده را آماده و وارد می‌کند:
  - `schedule.py`: برنامه اقساط شمسی؛
  - `contracts.py`: ساخت قرارداد؛
  - `legacy.py`: نگاشت اشخاص هلو؛
  - `statement_import.py`: Import صورت‌حساب بانک؛
  - `snapshot_import.py`: Import گزارش سامانه بتا؛
  - `trial.py`: اجرای آزمایشی روی فایل‌های واقعی، با خروجی فقط تجمیعی.

## چه چیزی پیاده شده است
| موضوع | پیاده‌سازی |
|---|---|
| پرونده هویتی واحد (D-18) | کد ملی معتبر و یکتا. کد تکراری یا نامعتبر منبع فقط `national_id_claim` است و ادغام خودکار نمی‌شود. نامزد ادغام «قوی» (کد ملی) و «مشکوک» (نام) وجود دارد. ادغام و بازگشت ادغام فقط با مجوز `party.merge`، علت و Audit انجام می‌شود. **قراردادها ادغام نمی‌شوند، فقط جابه‌جا می‌شوند** |
| Legacy هلو | `party_legacy_code` نگاشت چند کد هلو به یک شخص است و کد، نام، کد ملی و حساب‌های قدیمی را با lineage (اولین و آخرین Import و هش ردیف) نگه می‌دارد. `legacy_balance` مانده حساب‌های اشخاص هلو است. **فقط از `holoo_mirror` خوانده می‌شود و چیزی در آن نوشته نمی‌شود** |
| طرح و حساب بتا | `beta_scheme` با صاحب طرح و حساب بانکی واریز؛ چند طرح هم‌زمان. نرخ سهم بانک نسخه‌دار است (۱ تا ۱۰٪، تغییرناپذیر) |
| قرارداد | چند قرارداد هم‌زمان برای هر شخص. شناسه بانکی در هر طرح یکتاست. اجزای کالا، سهم بانک و کارمزد الماس شهر جدا نگه داشته می‌شوند (D-15). پس از فعال‌سازی تغییرناپذیر است و اصلاح از منبع به `contract_amendment` برای بررسی می‌رود |
| اقساط | کف (مبلغ کل ÷ تعداد) و باقی‌مانده روی قسط آخر (قابل تنظیم؛ اثبات‌نشده، E15). سررسیدها آخر ماه شمسی‌اند و تاریخ قسط اول از منبع می‌آید. وضعیت هر قسط **مشتق** است: `not_due`، `due`، `overdue`، `partial`، `paid_by_bank`، `paid_direct`، `paid_mixed`، `collected_per_beta` (طبق سامانه بتا، تأییدنشده با بانک)، `cancelled` |
| سقف توان قسط (D-17) | هنگام فعال‌سازی، جمع اقساط ماهانه همه قراردادهای فعال شخص با سقف معتبر مقایسه می‌شود. بدون سقف فقط با مجوز `beta.capacity_override` و یادداشت ممکن است (کنترل B-06). قرارداد واردشده از بتا وضعیت `imported_from_beta` دارد |
| وصول بانکی و پرداخت مستقیم | `receipt` تغییرناپذیر است و اصلاح فقط با ابطال انجام می‌شود. `apply_receipt` پول را فقط به **همان قسط مشخص** تخصیص می‌دهد و هرگز خودش قسط دیگری انتخاب نمی‌کند |
| اضافه‌وصول و استرداد (D-16) | وصول تکراری یا مازاد به `overpayment_credit` تبدیل می‌شود. گیرنده پیش‌فرض استرداد، پرداخت‌کننده مستقیم همان قسط است. استرداد با مجوز انجام می‌شود و به همان بستانکاری وصل است. تخصیص مجدد فقط دستی و با مجوز است. **هیچ تهاتر یا حذف خودکاری وجود ندارد** |
| لغو اقساط | فقط قسط بدون پرداخت لغو می‌شود. لغوهایی که از Import بتا می‌آیند در وضعیت `pending_review` می‌مانند |
| سهم بانک (Q-2) | `bank_share_withdrawal` در ابتدا «نامزد» است، تخصیص چند-به-یک دارد و به طلب مشتری دست نمی‌زند |
| ثبت حسابداری (D-14) | هنوز سندی صادر نمی‌شود. هر رویداد فیلد `journal_entry_id` دارد و `beta_unposted` یا B-12 فهرست رویدادهای ثبت‌نشده را نشان می‌دهد. قاعده ثبت پس از D-14 اضافه می‌شود و نیازی به تغییر جدول‌ها ندارد |
| Import صورت‌حساب | Idempotent است: هش فایل + کلید طبیعی ردیف (ردیف‌های تکراری در صورت‌حساب‌های هم‌پوشان فقط یک بار ثبت می‌شوند). پیوستگی موجودی کنترل می‌شود. هر ردیف دسته‌بندی می‌شود: قسط، نامزد سهم بانک، کارمزد، سایر واریز، سایر برداشت. تطبیق این‌طور است: شناسه واریز (کد ملی) ← شخص ← قراردادهای طرحِ همان حساب ← قسط بازِ هم‌مبلغ در بازه سررسید + سازگاری نام. `auto_apply` صریح است و پیش‌فرض آن خاموش است |
| Import گزارش بتا | طرح را **کاربر صریحاً** انتخاب می‌کند (Q-1). هر فایل یک Snapshot تغییرناپذیر است. قرارداد تازه ساخته و فعال می‌شود. تغییرها به اصلاحیه برای بررسی تبدیل می‌شوند. اضافه شدن اقساط حذف‌شده به لغو در انتظار بررسی تبدیل می‌شود. تعداد وصول‌شده به کنترل B-13 و B-14 می‌رود |
| کنترل‌ها | `core.beta_controls(as_of)`: از B-01 تا B-14 |

## آزمون‌ها
`HOLOO_PG_TEST_DSN=... python -m pytest beta/tests`، شامل ۳۱ آزمون:
- برنامه اقساط؛
- قواعد پایگاه داده؛
- نگاشت Legacy با Mirror ساختگی (Idempotency، Backup جدیدتر، سال دیگر، دست‌نخوردن Mirror)؛
- Import صورت‌حساب و Import گزارش بتا.

## اجرای آزمایشی روی فایل‌های واقعی (۱۴۰۵/۰۷)
`python -m beta.trial --pg <scratch db> --statement … --beta-export … --export-scheme unassigned|this [--auto-apply]` روی پایگاه آزمایشی که شامل کپی `holoo_mirror` است.

| مرحله | نتیجه |
|---|---|
| نگاشت اشخاص هلو ۱۴۰۴ | ۳۲,۶۹۶ پرونده. ۲۷,۲۸۶ کد ملی تأییدشده و ۸۱۵ ادعای کد ملی (تکراری یا نامعتبر). ۳۲,۷۰۵ مانده Legacy. نامزد ادغام: ۴۴ «قوی» (کد ملی) و ۲,۷۰۶ «مشکوک» (فقط نام، برای بررسی انسانی) |
| اجرای دوباره نگاشت | **صفر تغییر** (Idempotent)، و `holoo_mirror` دست‌نخورده |
| مانده بتای هلو | ۲۵۹ حساب با مانده غیرصفر، جمع ۶۳.۵ میلیارد ریال (B-11: هنوز بدون قرارداد در سیستم جدید) |
| Import گزارش سامانه بتا (در طرح جداگانه «نامشخص»، Q-1) | ۵۵۲ قرارداد و ۵۱۶ شخص (۴۹۹ شخص تازه). **صفر مغایرت برنامه اقساط**، یعنی قاعده کف روی همه ۵۵۲ قرارداد برقرار است. ۴۱۱ لغو قسط در انتظار بررسی. Import دوباره: `duplicate` |
| Import صورت‌حساب | ۴۰۰ ردیف و پیوستگی موجودی سالم. دسته‌بندی: ۳۵۱ قسط، ۲ نامزد سهم بانک (۱.۰۴ میلیارد)، ۲۳ کارمزد، ۱۳ سایر واریز، ۱۱ سایر برداشت. Import دوباره: `duplicate` |
| تطبیق اقساط | **شخص برای ۳۴۷ از ۳۵۱ واریز شناسایی شد (۹۸.۹٪)**؛ ۳۳۲ ردیف مشتری بتای هلو است. ۴ واریز بی‌شخص است (مشتری تازه‌ای که در هلو ۱۴۰۴ نیست). **تطبیق در سطح قسط: صفر**، چون قراردادها و اقساط این طرح در دسترس نیستند (Q-1) |
| سناریوی فرضی: گزارش بتا مال همین طرح باشد (`--export-scheme this --auto-apply`) | فقط ۷ واریز قرارداد پیدا کردند و هر ۷ به بررسی انسانی رفتند (مبلغ یا نام ناسازگار). **هیچ دریافتی خودکار ثبت نشد.** این تأیید دیگری است که آن گزارش پرتفوی این حساب نیست (E16) |

**نتیجه:** زنجیره Import و تطبیق روی داده واقعی کار می‌کند. برای رسیدن به تطبیق خودکار در سطح قسط فقط یک ورودی کم است: **گزارش قراردادهای بتا برای همین طرح** (Q-1).

## سرویس‌های بتا (API) و نمایندگان — هسته v0.21
مرجع: `docs/BETA_API_FA.md`؛ شاهد E27. سند مبنا بازنگری ۱.۳ (۱۴۰۲) است و **برای امروز تأیید نشده است** (D-23).
- `api_client.py`: کلاینت HTTP. هر فراخوانی شاهد تغییرناپذیر است. بدون تنظیم `beta_api_mode` اجرا نمی‌شود و هیچ رازی ذخیره نمی‌کند.
- `api_flow.py`: سه قدم فروش، یعنی بررسی ← ارسال رمز ← تأیید. نتیجه نامعلوم خودکار با شناسه یکتا حل می‌شود. همگام‌سازی جدول اقساط و ساخت قرارداد مرکزی انجام می‌شود.
- `api_simulator.py`: شبیه‌ساز درون‌برنامه‌ای، فقط از روی متن سند، برای آزمون و آموزش. هرجا سند ساکت است، انتخاب شبیه‌ساز «فرض» علامت خورده و رفتار بانک نیست.
- آزمون‌ها در `migration/tests/test_beta_api_agents.py` (۱۷ آزمون) پوشش می‌دهند:
  - مسیر کامل فروش؛
  - پاسخ گم‌شده و Timeout؛
  - درخواست تکراری (4406)؛
  - وابستگی رمز به داده؛
  - محدودیت‌ها؛
  - دامنه دسترسی نماینده؛
  - کنترل‌های بانک در برابر الماس؛
  - سهم و پرداخت نماینده.
