# اصول دائمی پروژه

این اصول الزامات دائمی معماری‌اند. هر طراحی، کد یا تصمیمی که با آنها در تضاد باشد باید رد شود یا با تصمیم ثبت‌شده مالک استثنا بگیرد.

## اصل ۱ — سازگاری دائمی با Backup هلو
- Backup واقعی هلو (خانواده SQL Server native backup با Schema هلو، مانند `holoo1_1404`) **یکی از فرمت‌های ورودی اصلی و دائمی** سیستم است، نه نمونه موقت.
- خواندن Backup یک **لایه مستقل** است: `Holoo Backup Reader → Extraction → Mapping → Normalization → Validation → Reconciliation → Import / Analytics`. این لایه به هسته حسابداری وابستگی شکننده ندارد و فقط از طریق **مدل Canonical نسخه‌دار** با آن حرف می‌زند.
- Reader باید **نسخه/Profile** هر Backup را تشخیص دهد (Schema fingerprint، نسخه هلو، سال مالی) و برای Profile جدید **Adapter** قابل افزودن داشته باشد. Backup ناشناخته رد نمی‌شود؛ با گزارش تفاوت Schema در حالت «تحلیل محدود» خوانده می‌شود.
- هر Import **قابل Audit** است: هش فایل، متادیتای Backup، Profile، نسخه Reader، زمان، کاربر، شمارش‌ها و نتایج کنترل ذخیره می‌شود.
- هر Import **قابل Reconciliation** است: مانده‌ها، موجودی و وضعیت چک‌ها از داده خام بازمحاسبه و با مقادیر ذخیره‌شده هلو مقایسه می‌شود.
- **Idempotent**: Import دوباره همان Backup هیچ رکورد تکراری نمی‌سازد. Import نسخه جدیدتر همان سال فقط **تفاوت‌ها** را ثبت می‌کند (افزوده، تغییر، حذف در منبع) و آنها را به‌عنوان رویداد تغییر منبع نگه می‌دارد.
- در دوره گذار، Backupهای تازه هلو مکرراً وارد می‌شوند تا گزارش‌ها و تحلیل‌ها روی تازه‌ترین داده اجرا شوند.

## اصل ۲ — حفظ اطلاعات و قابلیت‌های اصلی
- هیچ داده یا قابلیت دارای ارزش عملی هلو صرفاً به دلیل تفاوت معماری حذف نمی‌شود.
- معیار: **Holoo Compatibility Matrix** با دسته‌های A (حفظ عین منطق)، B (حفظ با طراحی بهتر)، C (جایگزین مدرن) و D (نیازمند تصمیم). هر ردیف `MUST` باید پیاده و با **آزمون برابری** روی Backup واقعی تأیید شود.

## اصل ۳ — تکرار ضعف‌ها ممنوع
- هر ضعف کشف‌شده در `WEAKNESS_REGISTER_FA.md` با طراحی جایگزین و **آزمون پذیرش** ثبت می‌شود و بسته شدن آن باید با آزمون اثبات شود.

## اصل ۴ — فراتر از هلو
- قابلیت‌های جدید (داشبورد، تحلیل سود، ریسک چک، نقدینگی، کشف ناهنجاری، هشدار با توضیح علت، API، هوش مصنوعی کنترل‌شده، گزارش چندساله) مجازند، به شرط **ارزش اثبات‌شده** و عدم تضعیف کنترل‌ها.
- خروجی‌های هوش مصنوعی فقط **پیشنهاد و توضیح** هستند و هیچ سند مالی را بدون تأیید انسانی تغییر نمی‌دهند.

## اصل ۵ — Evidence First
- هیچ قاعده‌ای فقط از روی نام جدول یا شباهت قطعی نمی‌شود. سطوح اثبات: `PROVEN` / `NEEDS_MORE_EVIDENCE` / `UNPROVEN`.
- شواهد (SQL، اسکریپت، خروجی) در مخزن نگه داشته می‌شوند و قابل اجرای مجددند.
- یافته‌ای که یافته قبلی را نقض کند، سند قبلی را **با ثبت دلیل** اصلاح می‌کند (تاریخچه اصلاحات).
- **هشدار ثبت‌شده:** کد SQL داخل Backup متعلق به نسخه هلوی زمان تهیه Backup است و لزوماً رفتار سال‌های قبل را نشان نمی‌دهد. قواعد باید با داده اثبات شوند.

## قواعد اجرایی
- داده واقعی (Backup، اطلاعات شخصی) هرگز در مخزن قرار نمی‌گیرد. فقط کد، Schema، شواهد تجمیعی و گزارش‌ها.
- هر مرحله مهم Commit و Push می‌شود.
- تصمیم‌هایی که انتخاب تجاری یا حسابداری مالک را تغییر می‌دهند در `OWNER_DECISIONS_FA.md` ثبت می‌شوند. کارهای فنی مستقل از آنها متوقف نمی‌شوند.
