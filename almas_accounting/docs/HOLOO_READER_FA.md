# طراحی لایه Holoo Backup Reader

> تحقق اصل دائمی ۱. این لایه یک **محصول مستقل** است و فقط از طریق مدل Canonical نسخه‌دار با هسته حسابداری ارتباط دارد.

## ۱. خط لوله

```
 ┌──────────┐   ┌──────────┐   ┌───────────┐   ┌──────────┐   ┌───────────────┐   ┌────────────┐   ┌──────────────┐   ┌──────────────┐
 │ Acquire  │ → │ Restore  │ → │ Profile   │ → │ Extract  │ → │ Map+Normalize │ → │ Validate   │ → │ Reconcile    │ → │ Load/Publish │
 │ hash,zip │   │ SQL srv  │   │ detect    │   │ raw rows │   │ canonical     │   │ integrity  │   │ vs Holoo     │   │ idempotent   │
 └──────────┘   └──────────┘   └───────────┘   └──────────┘   └───────────────┘   └────────────┘   └──────────────┘   └──────────────┘
        │              │              │               │                │                  │                 │                   │
        └──────────────┴──────────────┴───────────────┴────── ImportRun (Audit: همه متادیتا، شمارش‌ها، گزارش‌ها) ──────────────┘
```

| مرحله | ورودی | خروجی | نکات کلیدی |
|---|---|---|---|
| **Acquire** | فایل‌های `.bak`، ZIP یا ZIP چندتکه | فایل Backup + SHA-256 | الحاق تکه‌ها، هش، ثبت در `import_run`. فایل اصلی هرگز تغییر نمی‌کند. |
| **Restore** | Backup | دیتابیس موقت فقط‌خواندنی | SQL Server در Container یک‌بارمصرف. `RESTORE HEADERONLY/FILELISTONLY` ذخیره می‌شود. `DBCC CHECKDB` اجرا می‌شود. |
| **Profile** | دیتابیس | `profile_id` + گزارش تفاوت | Fingerprint = هش مرتب‌شده (جدول، ستون، نوع) جداول کلیدی + نسخه هلو (از Log ورود) + `DatabaseVersion` + سال مالی (از مسیر فایل و بازه تاریخ اسناد). |
| **Extract** | دیتابیس + Adapter | Bronze: یک فایل Parquet برای هر جدول + `row_hash` | فقط `SELECT`. Encoding با Collation `Arabic_CI_AS`. هش هر ردیف روی مقادیر خام. |
| **Map + Normalize** | Bronze | Silver: مدل Canonical (DuckDB/Parquet؛ DDL سازگار با PostgreSQL) | کلید منبع پایدار، ترمیم متن (Mojibake)، تاریخ میلادی + شمسی، نگاشت انواع (Fac_Type، Sanad_Type، State چک)، کالای یکپارچه × انبار. |
| **Validate** | Silver | `validation_report` | کنترل‌های C-01…C-21 و E-xx: توازن، یتیم‌ها، شکاف شماره، تاریخ خارج دوره و… |
| **Reconcile** | Silver + مقادیر ذخیره‌شده هلو | `reconciliation_report` | بازمحاسبه مانده‌ها (مقایسه با `SARFASL.Mandeh`)، موجودی (مقایسه با `ARTICLE.Exist`)، COGS و سند بستن، سیستم چک↔دفتر، مؤدیان↔دفاتر. |
| **Load / Publish** | Silver + گزارش‌ها | `holoo_mirror` در پایگاه اصلی + تحلیل‌ها | Idempotent. گیت: اگر کنترل «مسدودکننده» قرمز باشد، انتشار متوقف می‌شود ولی Silver برای تحلیل باقی می‌ماند. |

## ۲. Profile و Adapter
- **Profile** = ترکیب «خانواده Schema هلو» + «سال مالی». نمونه فعلی: `holoo-sql2014-schema@1405.06` (برنامه نسخه `1405.06.18`، DB version 782)، سال مالی ۱۴۰۴.
- **Adapter** = نگاشت جدول و ستون هلو به Canonical برای یک خانواده Schema. Adapterها اعلانی‌اند (YAML/Python dict)، نسخه دارند و آزمون واحد دارند.
- **رفتار در برابر Schema ناشناخته:**
  - ستون اضافه ← نادیده گرفته و گزارش می‌شود.
  - ستون لازم حذف‌شده ← Adapter خطای صریح می‌دهد.
  - جدول کلیدی ناموجود ← Import در حالت «تحلیل محدود» ادامه پیدا می‌کند.
- **Fingerprint کلیدی** روی جداول `SANAD, SND_LIST, SARFASL, CUSTOMER, FACTURE, FACTART, ARTICLE, Check, Check_Event, Process, TaxLog, M_GROUP, S_GROUP, Cash, ACOUND_N` محاسبه می‌شود. تغییر در ستون‌های کم‌اهمیت (مثل ۱۰۰ سطح قیمت) Profile را نمی‌شکند.

## ۳. کلیدهای پایدار و Idempotency
هر رکورد Canonical این ستون‌ها را دارد:

| ستون | معنا |
|---|---|
| `source_system` | `holoo` |
| `source_db` | نام DB هلو (مثلاً `holoo1_1404`) |
| `fiscal_year` | ۱۴۰۴ |
| `source_key` | کلید طبیعی منبع (جدول زیر) |
| `row_hash` | SHA-256 مقادیر خام نرمال‌شده |
| `first_import_run` / `last_import_run` | Lineage |

| موجودیت | کلید طبیعی هلو |
|---|---|
| حساب | `Col_Code+Moien_Code+Tafzili_Code` |
| شخص | `C_Code` |
| سند | `Sanad_Code` (شماره ثابت) |
| ردیف سند | `Sanad_Code` + `Index` |
| فاکتور/حواله | `Fac_Type` + `Fac_Code` |
| ردیف فاکتور | `Fac_Type` + `Fac_Code` + `A_Code` + `A_Index` |
| کالا (منبع) | `A_Code` |
| چک | `Check_Code` |
| رویداد چک | `Check_Event.Id` |
| Log | `Process.ID` |
| ارسال مالیاتی | `TaxLog.Id` |

- **Import مجدد همان Backup** (همان SHA-256) ← No-op. `import_run` جدید با وضعیت `duplicate_of` ثبت می‌شود.
- **Backup جدیدتر همان سال** ← مقایسه `row_hash`. رکوردهای جدید، تغییریافته و «حذف‌شده در منبع» به‌صورت **رویداد تغییر منبع** (`source_change`) ثبت می‌شوند. هیچ رکوردی بی‌صدا بازنویسی یا حذف نمی‌شود و آینه (`holoo_mirror`) نسخه‌دار است.
  - نکته: `Sanad_Code_C` در هلو بازشماره‌گذاری می‌شود. پس کلید، شماره **ثابت** است و شماره عطف فقط یک ویژگی است.
- **سال‌های مختلف** ← `source_db` و `fiscal_year` در کلید آمده‌اند، پس شماره‌های تکراری بین سال‌ها تداخل ندارند. اتصال زنجیره سال‌ها از طریق افتتاحیه↔اختتامیه کنترل می‌شود.

## ۴. نرمال‌سازی‌های ضروری (از یافته‌های اثبات‌شده)
| موضوع | قاعده | منبع شاهد |
|---|---|---|
| متن | `varchar` با cp1256 از طریق Collation؛ تشخیص و ترمیم Mojibake (latin-1 ↔ cp1256)؛ یکسان‌سازی ی/ك عربی و فارسی فقط در **فیلد جست‌وجو**، نه در مقدار اصلی | E05 |
| تاریخ | میلادی ذخیره‌شده ← نگه‌داری میلادی + تولید شمسی. `DateUser` دو قالب دارد (`yyyy/mm/dd` و `yyyy-mm-dd`). ساعت فاکتور نامعتبر است؛ زمان واقعی از Log گرفته می‌شود. | E10.6 |
| نوع فاکتور | F، K، X، Y، Z، S/D، **Q=ابطال‌شده**، P=پیش‌فاکتور (در `FBAILPRE`) | E01 |
| موجودی | فرمول مقدار (Q بی‌اثر). کالا = (مدل، انبار)؛ انبار = `M_GROUP` | E11 |
| چک | وضعیت از `Check_Event`، نه از پرچم‌های `Check`. مرتب‌سازی (تاریخ، Id) + هشدار برای ناسازگاری ترتیب | E08.10 |
| شخص | اجتماع حساب بدهکار و بستانکار. شناسایی لیست سیاه از پرچم و متن نام | A-12 |
| شماره سفارش وب | استخراج از `Fac_Comment` با الگوی `…/<digits>` | E10.2 |
| Blob Log | ذخیره خام + (فاز بعد) Parser ADTG برای نسخه‌های سند | E05.6 |

## ۵. کنترل‌های Reconciliation (گیت انتشار)
| کد | کنترل | سطح |
|---|---|---|
| R-01 | توازن همه اسناد | مسدودکننده |
| R-02 | یتیم‌ها (ردیف↔سند، فاکتور↔ردیف، ردیف↔کالا، فاکتور↔شخص، رویداد↔چک) = 0 | مسدودکننده |
| R-03 | مانده بازمحاسبه‌شده = `SARFASL.Mandeh` (با گزارش استثناها) | هشدار |
| R-04 | موجودی بازمحاسبه‌شده = `ARTICLE.Exist` | هشدار |
| R-05 | سند فاکتور = مبلغ فاکتور | هشدار |
| R-06 | چک↔دفتر (104/402) | هشدار |
| R-07 | پس از اختتامیه همه حساب‌ها صفر | هشدار (در ۱۴۰۴: ۴ حساب، علت معلوم) |
| R-08 | افتتاحیه = اختتامیه سال قبل (وقتی Backup سال قبل موجود است) | هشدار |
| R-09 | شمارش رکوردها Bronze = Silver (بدون گم‌شدن) | مسدودکننده |

نتیجه هر کنترل = `{status, expected, actual, diff, evidence_query, explanation}`. توضیح استثناهای شناخته‌شده (مثل Q) از کاتالوگ «استثناهای مستند» خوانده می‌شود تا هشدار تکراری تولید نشود.

## ۶. ذخیره‌سازی
- **Bronze:** `imports/<sha256>/bronze/<table>.parquet` (خارج از مخزن کد)
- **Silver:** `imports/<sha256>/silver.duckdb` (DDL در `holoo_reader/canonical/schema.sql`)
- **Registry:** `imports/registry.duckdb` شامل جداول `import_run`، `source_file`، `profile` و `report`
- **Mirror در پایگاه اصلی (PostgreSQL):** Schema `holoo_mirror` با همان DDL به‌علاوه ستون‌های Lineage و جداول `source_change`

## ۷. امنیت و حریم خصوصی
Backup و Silver شامل داده شخصی‌اند. رمزگذاری در حالت ذخیره، دسترسی نقش‌محور، و **عدم ذخیره رمزهای `USERDB`** (ستون‌های `PasWord` و `BackupPassWord` در Extract حذف می‌شوند).

## ۸. آزمون‌ها
- **Golden tests** روی Backup ۱۴۰۴: شمارش‌ها، جمع‌ها و نتایج R-xx باید با اعداد اثبات‌شده گزارش مهندسی معکوس برابر باشند (مثلاً 47,447 سند؛ COGS 7,699,284,125,059؛ 4 حساب پس از اختتامیه).
- **Idempotency test:** دو بار Import همان فایل ← صفر رکورد جدید.
- **Change test:** Import با تغییر مصنوعی یک ردیف ← دقیقاً یک `source_change`.
