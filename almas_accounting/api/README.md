# api — درگاه واحد برنامه برای هسته حسابداری

این API **هیچ قاعده کسب‌وکاری** ندارد. همه قواعد، مجوزها و کنترل‌ها در خود پایگاه داده اجرا می‌شوند. API فقط عملیات‌های فهرست‌شده در کاتالوگ هسته (`core/schema/013_ai_catalog.sql`) را اجرا می‌کند. به همین دلیل رابط کاربری انسان و عامل هوش مصنوعی از **یک درِ مستند و یکسان** وارد می‌شوند.

| مسیر | کار |
|---|---|
| `GET /operations` | آنچه کاربر یا عامل اکنون مجاز است انجام دهد، با هدف، راه برگشت و پشتوانه |
| `POST /operations/{name}` | اجرای یک عملیات با آرگومان‌های **نام‌دار** که با تعریف تابع کنترل می‌شوند |
| `GET /schema` | توضیح خود هسته: جدول‌ها، View‌ها و توابع |
| `GET /health` | سلامت اتصال |

## تضمین‌ها
- **کاربر اقدام‌کننده را API تعیین می‌کند:** مقدار `p_user` / `p_by` / `p_created_by` از هویت احرازشده می‌آید. اگر فراخواننده آن را بفرستد، درخواست رد می‌شود (۴۲۲)، پس کسی نمی‌تواند به نام دیگری عمل کند.
- **مجوز در پایگاه اجرا می‌شود:** نبود مجوز پاسخ ۴۰۳ می‌دهد و نقض قاعده پاسخ ۴۰۰ با پیام خود قاعده. تصمیم‌های مخصوص انسان برای عامل AI رد می‌شوند.
- **هر نوشتن در همان تراکنش در `core.audit_event` ثبت می‌شود:** عملیات، آرگومان‌ها، کانال و یادداشت.
- **مبلغ‌ها رشته برمی‌گردند** و هرگز از عدد اعشاری (float) عبور نمی‌کنند.

## احراز هویت
`authenticate()` جایگاه اتصال به سامانه هویت هنگام استقرار است: رمز با Argon2 و MFA برای مدیر (W-14). سرآیند توسعه `X-Almas-User` **فقط** با `ALMAS_API_DEV_AUTH=1` پذیرفته می‌شود و در استقرار واقعی خاموش است.

```bash
ALMAS_PG_DSN=... ALMAS_API_DEV_AUTH=1 uvicorn api.app:app      # فقط توسعه
```
آزمون‌ها: `api/tests` (۸ آزمون).

## رابط کاربری (`api/static/index.html`، نشانی `/ui/`)
صفحه ساده فارسی و راست‌به‌چپ، سازگار با موبایل و حالت تیره. **هیچ منطقی ندارد** و همه چیز را فقط از همین API می‌خواند. زبانه‌ها:
- کارتابل کنترل‌ها (مرتب بر شدت)؛
- تراز چهارستونی (سال و بازه دلخواه)؛
- سن‌بندی مطالبات؛
- عملیات مجاز کاربر، با راه برگشت و پشتوانه هر عملیات.

زبانه‌ها (همه فقط با عملیات کاتالوگ):

| زبانه | کار |
|---|---|
| کارتابل کنترل‌ها | همه کنترل‌های سیستم، مرتب بر شدت |
| فاکتور فروش / فاکتور خرید | یک فرم مشترک: شخص، کالا، انبار، تعداد، قیمت، تخفیف ردیف، هزینه‌های فاکتور خرید و دریافت/پرداخت همان لحظه. «ثبت نهایی» در یک گام ایجاد، قطعی و ثبت می‌کند و **سند حسابداری حاصل** را نشان می‌دهد |
| برگشت | یافتن فاکتور، ردیف‌ها با مقدار قابل برگشت، علت؛ ثبت و نمایش سند |
| دریافت وجه / پرداخت وجه | یک فرم مشترک: شخص، مبلغ، صندوق یا بانک، شرح |
| تطبیق حساب شخص | حساب‌های فرعی شخص با بدهی و بستانکار باز، و «تطبیق خودکار» (قدیمی‌ترین بدهی اول؛ هر تخصیص با علت قابل برگشت است) |
| سن‌بندی حساب اشخاص، تراز چهارستونی، گزارش مدیریتی (فروش و سود ناخالص ماهانه، موجودی)، عملیات مجاز من | گزارش‌ها |

- **تاریخ شمسی ورود و نمایش داده می‌شود** و استاندارد ذخیره می‌شود. تبدیل با تقویم ایرانی خود مرورگر انجام می‌شود، بدون الگوریتم دست‌نویس.
  - رفت‌وبرگشت برای **۱,۸۵۸ روز پیاپی (۱۴۰۲ تا ۱۴۰۶)، از جمله ۳۰ اسفند ۱۴۰۳ کبیسه، بدون خطا** بررسی شد.
- فروش زیر قیمت خرید تأیید و علت می‌خواهد (D-06). فروش بیش از موجودی رد می‌شود و فاکتور پیش‌نویس می‌ماند. کد حساب هرگز به شکل مبلغ نمایش داده نمی‌شود.
- **چرخه کامل در Chromium با داده ساختگی اجرا شد:** خرید، فروش، برگشت، دریافت، پرداخت، تطبیق و سن‌بندی نهایی صفر.

آزمون‌ها: `api/tests` (۸ آزمون).

## رابط کاربری (`api/static/index.html`، نشانی `/ui/`)
صفحه ساده فارسی و راست‌به‌چپ، سازگار با موبایل و حالت تیره. **هیچ منطقی ندارد** و همه چیز را فقط از همین API می‌خواند. زبانه‌ها:
- کارتابل کنترل‌ها (مرتب بر شدت)؛
- تراز چهارستونی (سال و بازه دلخواه)؛
- سن‌بندی مطالبات؛
- عملیات مجاز کاربر، با راه برگشت و پشتوانه هر عملیات.

زبانه‌های ثبت:
- **فاکتور فروش:** جست‌وجوی مشتری و کالا، انتخاب انبار، ردیف‌ها و دریافت همان لحظه. «ثبت نهایی» در یک گام ایجاد، قطعی و ثبت می‌کند.
  - فروش زیر قیمت خرید، تأیید و علت می‌خواهد (D-06).
  - فروش بیش از موجودی با پیام صریح رد می‌شود و فاکتور پیش‌نویس می‌ماند.
- **دریافت وجه:** شخص، مبلغ و صندوق یا بانک.

تاریخ‌ها استاندارد ذخیره و **شمسی نمایش داده می‌شوند** (Intl مرورگر، بدون کتابخانه). کد حساب هرگز به شکل مبلغ نمایش داده نمی‌شود.

چرخه کامل با Chromium روی داده ساختگی اجرا شد: ثبت فاکتور، ثبت دریافت و مشاهده سن‌بندی. آزمون خودکار `api/tests/test_documents.py` کل چرخه را فقط از راه API می‌آزماید: خرید، فروش، رد فروش بیش از موجودی، برگشت و دریافت.

## بازبینی روی دفتر واقعی (فقط محیط امن و داخلی)
```bash
bash build_audit.sh      # پایگاه تازه + انتقال کامل ۱۴۰۴ + همه برابری‌ها (migration/audit_run.py)
psql "$ALMAS_PG_DSN" -c "INSERT INTO core.app_user (username) VALUES ('reviewer')"   # فقط مشاهده: هیچ مجوز ثبتی ندارد
ALMAS_PG_DSN=... ALMAS_API_DEV_AUTH=1 uvicorn api.app:app --host 127.0.0.1
```
پایگاه بازبینی شامل داده شخصی است. باید فقط روی شبکه داخلی باشد و پس از بازبینی حذف شود.
